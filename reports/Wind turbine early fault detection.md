# Beat 0.66 by Persisting Residual Alarms

The published bar for SCADA early fault detection on CARE to Compare is still the Fraunhofer IEE per-turbine autoencoder at a **pooled CARE score of 0.66 across all 95 datasets**. Random flagging scores 0.5, "all normal" and "all anomaly" both score 0, and an isolation forest falls below 0.5 ([Gück et al., Data 2024](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content)). No peer-reviewed 2024–2026 paper reports an official-protocol CARE score, and no official per-farm number exists for Wind Farm A. CARE puts **40% of its weight on accuracy on normal datasets** and only counts an event as detected after a persistence counter reaches 72 (about 12 h of 10-minute data). The design target that follows is a conservative pipeline with persistent alarms: per-target normal-behaviour models (NBMs), robust z-scores conditioned on operating regime, and EWMA/CUSUM smoothing that feeds a criticality counter. A sensitive pointwise detector is the wrong target. Implementers need to match the reference code `energy_fault_detector.evaluation.CAREScore` rather than the paper, because the two differ in three places: earliness weighting, the accuracy cap comparison and the criticality window. Wind Farm A also needs special handling, since its status labels are synthetic and must be ignored at scoring time. On the product side, commercial wind condition-monitoring tools share one information architecture: fleet map and table, drill-down, alarm triage, cases linked to work orders, IEC 61400-26 availability and loss Pareto. None of them publishes lead-time definitions or false-alarm metrics, and a transparent prototype can stand out on exactly that point.

## CARE scoring is a persistence-gated, accuracy-heavy metric

CARE combines four sub-scores. **Coverage** is a pointwise F0.5. **Accuracy** is TN/(TN+FP) on normal datasets. **Reliability** is an event-level F0.5. **Earliness** is a weighted score that favours early flags inside the event window. The paper fixes weights of 1/1/1/2 and β = 0.5 throughout. It then defines two special cases: CARE = 0 if no anomalies are detected, and CARE = mean accuracy if that accuracy falls below 0.5 ([paper Eqs. 1–5](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content)). Reliability depends on a criticality counter. The counter adds 1 for each anomalous prediction at a normal-status timestamp, subtracts 1 (floored at 0) for each normal prediction, and stays frozen at abnormal-status timestamps. An event counts as detected when the counter's maximum reaches **72**, the threshold the authors found best across all 95 series, while noting that shorter events need lower thresholds ([paper Alg. 1](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content)). The paper's Algorithm 1 has a typo: it increments when status = 0 even though its own prose defines 1 as normal. The code and FAQ increment on normal-status points ([analysis.py](https://github.com/AEFDI/EnergyFaultDetector/blob/main/energy_fault_detector/utils/analysis.py)).

The reference implementation is the de facto standard, and it departs from the paper text in ways that move scores. The table lists the differences that matter.

| Element | Paper text | Reference code (`care_score.py`, `main` as of Oct 2026) |
|---|---|---|
| Earliness weights | 1 for the first half of the event, then linear decay to 0 | `ws_start_of_descend=(1,4)`: 1 for the first quarter, then decay; pass `(1,2)` to match the paper |
| Accuracy cap | CARE = Acc if Acc **<** 0.5 | returns avg accuracy if **≤** 0.5 |
| "No anomalies" rule | no anomalies detected | `sum(anomaly_detected)==0`, i.e. no *event* (normal or anomaly) reached the threshold |
| Criticality window | entire prediction frame | `predicted_anomalies.loc[:event_end]`, so the leading padding counts and post-event data does not |
| Detection test | threshold "exceeded" | `max_criticality >= 72`, with the counter capped at 1000 |
| Coverage ground truth | prediction frame, normal-status points | whole supplied series; abnormal status plus the `[event_start:event_end]` window = True, filtered to the normal index |
| Reliability | event-level F0.5 | one `fbeta_score` over all selected events, not an average |

Sources: [care_score.py](https://github.com/AEFDI/EnergyFaultDetector/blob/main/energy_fault_detector/evaluation/care_score.py) and [paper](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content). The constructor is `CAREScore(coverage_beta=0.5, reliability_beta=0.5, coverage_w=1., accuracy_w=2., earliness_w=1., reliability_w=1., criticality_threshold=72, min_fraction_anomalous=0.1, ws_start_of_descend=(1, 4), anomaly_detection_method='criticality')`. Each event goes through `evaluate_event(event_start, event_end, event_label, predicted_anomalies, normal_index, ..., ignore_normal_index)`, and `get_final_score()` then aggregates them. One trap: passing `criticality_threshold` to `get_final_score` permanently overwrites the instance attribute ([care_score.py](https://github.com/AEFDI/EnergyFaultDetector/blob/main/energy_fault_detector/evaluation/care_score.py)). The FAQ admits the exact original benchmark code is "not exactly" available. Nobody can confirm whether the published 0.66 used quarter-point or half-point earliness decay, so any reported score should state which setting was used ([FAQ](https://github.com/AEFDI/EnergyFaultDetector/blob/main/docs/care2compare_faq.rst)).

The scoring logic has direct consequences for detector design. Coverage is computed over the whole series, so false positives in the padding before and after the event cut its precision, and the F0.5 setting makes that cut steep. The counter is a bounded up/down walk, so flags at a duty cycle of 50% or less never trigger detection no matter how long they continue. Both the "all anomaly" and "all normal" strategies land in a special case that returns 0. Any detector therefore has to keep mean normal-event accuracy above 0.5 and produce at least one sustained run of flags. The paper attributes the autoencoder's 0.66 to "high accuracy on normal data and a good performance on the event based F1/2-score", held back by "an overall low number of detected anomalies" ([paper §4.3](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content)). That points to the gain available: raise coverage and earliness without giving up accuracy.

## Wind Farm A needs its own evaluation and cleaning rules

Wind Farm A contains 5 onshore EDP turbines in Portugal and 22 datasets with 86 features, of which 54 are sensors. Only power, reactive power and wind speed are named. Data are at 10-minute resolution, with one year of training data and 4–98 days of prediction data per dataset. Prediction windows include padding before and after each event so the event label cannot be guessed from the window ([paper Table 1, §3.1.2](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content)). EDP's logbook gives only the fault timestamp. The authors therefore **synthesised status labels**: status 4 for the 14 days before each fault and status 3 for the 3 days after. They also estimated event starts from the data, so the true onset is uncertain ([paper §3.1.3](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content); [arXiv v2](https://arxiv.org/html/2404.10320v2)). The consequence is set out in the official notebook and guide. For Farm A, status may be used only to filter training data. Scoring must pass `ignore_normal_index=True`, which evaluates every prediction timestamp and moves the criticality counter at every step. Otherwise whole anomalous events would be filtered away ([notebook](https://github.com/AEFDI/EnergyFaultDetector/blob/main/notebooks/CARE%20to%20Compare/CARE%20to%20Compare.ipynb); [guide](https://github.com/AEFDI/EnergyFaultDetector/blob/main/docs/care2compare_guide.rst)). The notebook sets `ignore_normal_idx = {'A': True, 'B': False, 'C': False}`. Only rows with `train_test == 'prediction'` are scored.

The paper and the code also disagree on what counts as normal for training. The paper's Table 2 treats status 0 (normal) and status 2 (idling) as normal. The reference loader uses `status_type_id == 0` only ([care2compare.py](https://github.com/AEFDI/EnergyFaultDetector/blob/main/energy_fault_detector/evaluation/care2compare.py)). Since v5, Farm A's status 5 was remapped to 0 because it "came from a heuristic rather than ground truth", so Farm A in practice carries only statuses 0, 3 and 4. The authors further recommend checking power and wind speed rather than trusting status alone, for example flagging points where wind speed is in the operating range but power is near zero ([Zenodo v6](https://zenodo.org/records/15846963); [paper §3.1.4](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content)).

Version 6 is the current release (Zenodo 15846963, published 9 July 2025, 5.5 GB, CC BY-SA 4.0). It counts **45 anomaly and 50 normal datasets**, against the paper's 44/51. The v5→v6 changes are mostly metadata. Two Farm C sensors had their units changed from bar to hPa, the descriptions of events 34, 7 and 19 became "high temperature in transformer cell", the dates of events 44 and 47 were corrected, and the event_info date format was aligned with the data files. The labelling changes came earlier, in v5. Event 51 was relabelled as an anomaly, missing Farm A status-4 labels were added, Farm A status 5 became 0, and an `asset_id` column was added ([Zenodo v6](https://zenodo.org/records/15846963)). Which farm event 51 belongs to was not confirmed from primary data. An informal repo's Farm A split of 12 anomaly / 10 normal would fit if it is a Farm A event ([PeterImoniose repo](https://github.com/PeterImoniose/care-wind-turbine-predictive-maintenance)). Scores on v5 or v6 are therefore not strictly comparable to the published 0.66.

The data-quality issues are concrete. Across all farms, per-timestamp Min, Max and Std channels are often implausible: Std too large for the Min/Max/Avg, Min > Avg, Max < Avg, or all three zero. **Avg channels are generally plausible.** In Farm A, the grid reactive-power statistics show these issues, and the pitch angle wraps between 0° and 360° ([Zenodo v6](https://zenodo.org/records/15846963)). Timestamps are anonymised per file, with each file shifted to start in 2022, so files may overlap and cannot be ordered against each other ([FAQ](https://github.com/AEFDI/EnergyFaultDetector/blob/main/docs/care2compare_faq.rst)). In practice this means using Avg features only, sin/cos-encoding the pitch angle (the loader's `is_angle` flag does this), dropping counters, and never stitching event files into a continuous history.

## No one has published a verified Farm A score to beat

The only official number is the **pooled 0.66**. The paper's sub-scores appear only as bar charts, and the committed notebook that prints per-farm scores has no stored outputs ([paper §4.3](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content); [notebook](https://github.com/AEFDI/EnergyFaultDetector/blob/main/notebooks/CARE%20to%20Compare/CARE%20to%20Compare.ipynb)). The Farm A autoencoder used layers 44-25-4-25-44, learning rate 0.0018, noise 0.06, batch size 64, a 75/25 train/validation split, early stopping with patience 3, and the L2 reconstruction error as score. Its **adaptive threshold** is a small network (23 hidden units) that predicts the expected reconstruction error ε, and a point is flagged when the error exceeds ε + γ, with γ = 0.344 for Farm A ([paper Table 3](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content)). The official `windfarm_A.yaml` adds the preprocessing: 0.001/0.999 percentile clipping, columns dropped above 5% NaN, a low-unique-value filter, min-max scaling, RMSE score, and an adaptive threshold with smoothing parameter 6 ([c2c_configs](https://github.com/AEFDI/EnergyFaultDetector/tree/main/notebooks/CARE%20to%20Compare/c2c_configs)). The maintainers warn that results vary with random initialisation and recommend training 5–10 runs.

Every other number is informal or uses a different protocol. One GitHub project reports a Farm A CARE of **0.608** for a denoising autoencoder with PCA. Its breakdown is Coverage 0.261, Accuracy 0.989, Reliability 0.714 and Earliness 0.087, with 4 of 12 faults detected and no false alarms. The same project gives B 0.626 and C 0.731, and an isolation forest at 0.518 on Farm A. But it uses its own scorer, a criticality threshold of 36 rather than 72, and thresholds tuned on the scored events ([PeterImoniose repo](https://github.com/PeterImoniose/care-wind-turbine-predictive-maintenance)). Another unreviewed repo reports temperature-only NBMs scoring **0.49 (gradient boosting) and 0.47 (RC thermal model)** across the 95 datasets, below random ([wind-thermal-nbm](https://github.com/kwwaleszczynski-del/wind-thermal-nbm)). Nair et al. (arXiv 2510.15010, Oct 2025) use CARE data but report only AUC-ROC (Farm A 0.912) on their own split, which is not comparable ([arXiv 2510.15010](https://arxiv.org/html/2510.15010v1)). The informal breakdown does show the typical failure mode: near-perfect accuracy with low coverage and earliness. Its temperature-only results also suggest that NBMs limited to temperature targets miss the hydraulic and transformer events. A reasonable internal target for Farm A is above 0.6 under the official scorer, reported with the dataset version and the earliness setting. That target is an inference from these sources, not a published leaderboard figure.

## An interpretable NBM pipeline: model, normalise, persist, diagnose

**Regressors.** Evidence that 10-minute temperature NBMs need non-linear models is weak. Chesterman et al. compared elastic net, LightGBM, MLP and SVR. They found LightGBM and MLP only marginally better for some signals, and elastic net gave the best healthy/unhealthy separation for rotor-brush and generator-bearing failures. **During long cool-downs, SVR and LightGBM degraded severely**, while elastic net held up ([Chesterman et al., WES 2023](https://wes.copernicus.org/articles/8/893/2023/)). A DTU study takes the opposite view: neural NBMs beat linear regression, and leftover seasonality in linear residuals inflated alarm levels ([DTU Orbit](https://orbit.dtu.dk/en/publications/comparative-analysis-of-neural-network-and-regression-based-condi/)). Fraunhofer IWES got R² > 0.9 on 12 of 16 drivetrain temperatures with a semi-physical, interpretable NBM, and found 10-minute data sufficient ([Lichtenstein et al., Wind Energy 2025](https://onlinelibrary.wiley.com/doi/full/10.1002/we.2961)). The defensible stack is a per-target ridge or elastic-net baseline with a HistGradientBoosting or LightGBM challenger. Choose between them on healthy-versus-faulty separation and cool-down behaviour, not on RMSE alone.

**Inputs and leakage.** The standard drivers are active power, rotor speed and ambient temperature ([Letzgus, WES 2020](https://wes.copernicus.org/articles/5/1375/2020/)), plus wind speed, reactive power and pitch. The main risk is "simultaneity" features, meaning concurrent correlated sibling signals. In one IST Lisbon thesis they removed most of the fault-detection ability, because the NBM explains the fault away using a sibling that shares it ([Felgueira thesis](https://fenix.tecnico.ulisboa.pt/downloadFile/1970719973968215/Tese_Final_Telmo_Felgueira_79004.pdf)). Farm A's sensors are anonymised, so component groups have to be recovered by correlation clustering, and same-cluster signals excluded from each target's inputs. Lags of the target itself carry the same risk of explaining away a slow drift. Chesterman found three lags gave only marginal gains, so exogenous lags such as power over the last 30–60 minutes are the safer way to model thermal inertia.

**Healthy-data filtering.** Train only on status-normal, power-curve-consistent data. Letzgus removes data below 10% of rated power and data within ±60 days of detected change points. He found change points in **about one-third of 600 signals** over two years, detected with a kernel method at F1 = 0.86 ([Letzgus 2020](https://wes.copernicus.org/articles/5/1375/2020/)). Chesterman treats 4 months before to 1 month after a failure as unhealthy. He subtracts a **fleet median** per timestamp to separate weather from turbine-specific effects, and allows no missing values in the median when the fleet has fewer than 5 turbines ([Chesterman 2023](https://wes.copernicus.org/articles/8/893/2023/)). With 5 turbines, Farm A sits at that boundary. The median of the other four is usable, with a fallback to the per-turbine NBM whenever any value is missing.

**Regime-aware residual normalisation.** The robust standard is σ = **1.4826 × MAD**, re-estimated with iterative outlier removal and banded at 3, 4 and 5 robust σ ([Chesterman 2023](https://wes.copernicus.org/articles/8/893/2023/)). The CARE baseline's adaptive threshold, a learned expected error plus γ, shows that conditioning the scale on operating state is better than a single global σ ([paper §4.2](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content)). Bangalore's Mahalanobis distance on model errors is the multivariate version ([Chalmers](https://research.chalmers.se/en/publication/248521)), but it assumes normality, which breaks down with bimodal residuals during operational shifts ([MDPI JMSE 2025](https://www.mdpi.com/2077-1312/13/7/1337)). No source gives a canonical binning. A practical scheme is power deciles plus an idle bin, optionally crossed with ambient-temperature terciles. Each bin gets its own median and MAD from healthy validation data, with a minimum count and a fallback to the global value. Quantile GBMs at q = 0.05/0.5/0.95 are a smooth alternative.

**Alarm logic.** Wind papers rarely publish λ, L, k or h values. Chesterman uses CUSUM on 10/30/90/180-day subgroups and a health score built from moving averages of anomaly scores over 1–180 days. In his study, plain IOD–MAD thresholding detected 3 of 4 generator-bearing and 3 of 3 generator-fan cases, against 2 of 4 and 2 of 3 for CUSUM. That came at the cost of more unexplained flags, with a median false-positive ratio of about 0.08–0.12 on healthy turbines ([Chesterman 2023](https://wes.copernicus.org/articles/8/893/2023/)). One Renewable Energy study found **MEWMA more suitable than univariate EWMA** for early detection ([RePEc](https://ideas.repec.org/a/eee/renene/v115y2018icp808-816.html)). An XGBoost NBM with an EWMA chart gave only 3–4.25 h of warning ([IEEE Access 2020](https://doaj.org/article/17fdd44d48aa4a1eb476168e4818a1e5)). Seasonality-adjusted temperature residuals on 150 turbines gave **1–2 months** of lead time for gearbox, generator and main-bearing failures ([arXiv 1910.09808](https://arxiv.org/pdf/1910.09808)). The CARE criticality counter is the one persistence rule validated on this benchmark, so the alarm chain should end in it. The chain is: robust z per target, then EWMA (standard SPC defaults of λ ≈ 0.05–0.2 and L ≈ 2.7–3, not wind-validated) or CUSUM (k = 0.5σ, h = 4–5σ), then a binary flag, then the counter at 72. Tune the parameters on Farm A's normal datasets until accuracy stays near 0.9 or above, and clear alarms with hysteresis. In a pipeline built this way, the EWMA or CUSUM stage turns intermittent flags into the sustained runs the counter rewards.

**False-alarm control and diagnosis.** A data-quality layer comes before scoring. It covers flatline or stuck-sensor detection, range and rate-of-change checks, curtailment detection from pitch versus the power curve, masks for start-up and shutdown transients, and an icing proxy. Points failing these checks are marked non-normal so they neither raise nor clear alarms in production. CARE's Farm A scoring, by contrast, evaluates every point regardless. For diagnosis, per-target NBMs make attribution direct: the component whose residuals breach the threshold is the suspect. A large deviation in one input inflates autoencoder reconstruction error across many features, which is why Fraunhofer built ARCANA for root-cause attribution in its autoencoder framework ([arXiv 2401.07871](https://arxiv.org/pdf/2401.07871); [Fraunhofer](https://publica.fraunhofer.de/handle/publica/267752)). Letzgus adds a useful "unknown" trigger: simultaneous change points across signals that share a regressor point to an input problem, not a component fault ([Letzgus 2020](https://wes.copernicus.org/articles/5/1375/2020/)). "Unknown" is therefore a legitimate diagnosis output. It applies when component scores are close, when data-quality flags are active, or when several unrelated groups alarm at once.

## Commercial products converge on fleet, case and loss screens

The clearest public description of a screen set comes from Bazefield. Its FleetView is a "live map and table of all sites with real-time status indicators, active alarm counts, and headline production KPIs", with drill-down from fleet to region, site and asset. Around it sit live alarms and events filterable by severity, domain and site, case management, work orders, an IEC 61400-26 availability module and planner, and loss Pareto charts with financial impact ([Bazefield](https://product.bazefield.com/core.html)). XMPro adds the digital-twin pattern: a map with colour-coded status icons and a turbine twin where clicking a flagged section opens error details and linked recommendations. It also scores failure likelihood "with confidence" and supports what-if simulation ([XMPro](https://xmpro.com/solutions-library/intelligent-multi-location-windfarm-management/)). The KPIs that recur across products are production, time- and energy-based availability under IEC 61400-26-1:2019, lost production by category, performance ratio and capacity factor ([standard.no](https://online.standard.no/en/iec-61400-26-1-2019-ed1)). Greenbyte users complain that potential-power methods overstate grid-curtailment losses and that warning codes wrongly zero out availability ([Greenbyte Ideas](https://influence.powerfactors.app/forums/918697-greenbyte-ideas/filters/top?page=7)).

Vendors build an early-warning case from the same parts. GE SmartSignal shows the gap between model and actual, diagnostic rules giving a "probable cause", and "time-to-action forecasting" of when the alarm limit will be reached, all feeding case management and work orders ([GE Vernova](https://gevernova.com/software/blog/early-bearing-fault-detection-wind-turbine-prevents-14M-failure)). ONYX offers alert context, root-cause insights and full case history ([ONYX](https://www.onyxinsight.com/fleetmonitor/)). Clir grades departures from an "expected probabilistic range" at multiple severities and stresses "limited false positives" ([NAWindpower](https://nawindpower.com/clir-ai-software-detects-turbine-anomalies)). Siemens Gamesa filters **about 250,000 deviations a year down to about 8,000 site visits**, with expert triage in between ([SGRE](https://siemensgamesa.com/products-and-services/service-wind/diagnostics)). None of the public sources defines health-scale levels, colour palettes or case lifecycle state names. Red/amber/green is implied, not documented. Lead-time claims range from 6 months (Vestas) through 24 months (ONYX) to 3 years (SGRE), with no stated start or end points ([Vestas](https://vestas.com/content/dam/vestas-com/global/en/brochures/Condition_Monitoring_System.pdf.coredownload.inline.pdf); [ONYX](https://www.onyxinsight.com/fleetmonitor/); [SGRE](https://siemensgamesa.com/products-and-services/service-wind/diagnostics)).

For a 5-turbine prototype, this evidence supports the following dashboard. A fleet map paired with a sortable table, with status colour used only for severity. A turbine schematic on which components light up from residual alarms. An alarm and case list where each case card shows component and failure mode (or "unknown"), severity, first detection, lead time so far, projected time to threshold, a residual chart with the expected band, ranked contributing signals, confidence, owner, comments and status. A KPI strip with energy, both availabilities, and lost energy by category. Most products leave out a model-evaluation screen, and that is the opening. It would show CARE and its sub-scores, per-event detection and lead time, false alarms per turbine-month, and historical replay with clearly labelled fault injection. The case lifecycle (New → Acknowledged → Monitoring → Action planned → Closed as confirmed, false alarm or unknown) is a synthesis, since no vendor publishes theirs.

## Conclusion

On CARE, the benchmark rewards restraint. An alarm counts only after 12 hours of net-positive flags, and normal datasets carry double weight. A well-calibrated linear NBM with regime-conditioned robust z-scores and EWMA/CUSUM persistence can therefore plausibly compete with the autoencoder baseline while staying explainable per component. That is a hypothesis, untested in published work, and Farm A is a good test bed because its 22 events are small enough to iterate on quickly. The real risk is in reporting, more than in modelling. The reference code and the paper disagree, Farm A's labels are synthetic, the dataset changed under the published baseline, and no verified per-farm score exists. A result therefore means something only if it states the scorer version, the earliness setting, `ignore_normal_index=True`, the dataset version and the variance across seeds.

The commercial market shows the same gap. Vendors sell lead time and hit rates they never define, while the operators they serve fight alarm fatigue. A dashboard that applies CARE-style accounting to its own alarms, treating "unknown" as a valid answer and showing measured lead time and false-alarm cost next to each case, would add something no surveyed vendor shows publicly.
