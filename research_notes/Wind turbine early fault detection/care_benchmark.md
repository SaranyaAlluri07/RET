## Q1. Exact formulas for the CARE score and its four sub-scores

### Takeaway
CARE = 0 if no event is flagged; = mean normal-event Accuracy if that accuracy is below 0.5 (code: ≤ 0.5); otherwise the weighted average (1·Coverage + 1·Earliness + 1·Reliability + 2·Accuracy)/5. Coverage = pointwise F0.5 averaged over anomaly events; Accuracy = TN/(TN+FP) averaged over normal events; Reliability = event-level F0.5 where an event is "detected" if max criticality ≥ 72; Earliness = weighted score with weight 1 early in the event, then linear decay to 0 at the event end. The paper says decay starts at the event midpoint, but the reference code (default) starts it at 1/4 of the event. That is a documented discrepancy to note.

### Cited Findings

**Overall structure (paper, Section 3.2)**
- Four aspects: "1. Coverage: Detection of as many correct anomalies as possible; 2. Accuracy: Recognition of normal behavior; 3. Reliability: Few false alarm events; 4. Earliness: Detection of anomalies before faults become critical." — [Paper PDF §3.2.1](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content)

**Coverage (paper Eq. 1)**
- "the prediction time frame of a given anomaly event dataset is filtered. All data points with an abnormal status ID according to Table 2 are ignored... let g be the ground truth of all data points with a normal status ID within the prediction time frame and p is the corresponding prediction... Fβ(g,p) = (1+β²)·tp / ((1+β²)·tp + β²·fn + fp)" with "β = 1/2 ... to give more weight to precision than recall, thereby penalizing excessive false positives." — [Paper PDF Eq. 1](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content)
- Code: `fbeta_score(y_true=ground_truth, y_pred=predicted_anomalies, beta=self.coverage_beta)` with default `coverage_beta=0.5`. Ground truth = `~normal_index` (abnormal status counts as anomaly) and then `ground_truth.loc[event_start:event_end] = True` for anomaly events. Metrics are computed on `ground_truth[normal_index]`, `predicted_anomalies[normal_index]`, i.e., over the WHOLE supplied prediction series (not only the event window), restricted to normal-status points. — [care_score.py](https://github.com/AEFDI/EnergyFaultDetector/blob/main/energy_fault_detector/evaluation/care_score.py)
- FAQ: "Coverage is a pointwise F-score computed on anomalous events. The ground truth is: timestamps with anomalous status are anomalous, timestamps between event_start and event_end of anomalous events are also considered anomalous, all other timestamps are considered normal. For wind farm B and C the first type of true anomalies are ignored." — [care2compare_faq.rst](https://github.com/AEFDI/EnergyFaultDetector/blob/main/docs/care2compare_faq.rst)

**Accuracy (paper Eq. 2)**
- "Acc(g,p) = tn(g,p) / (fp(g,p) + tn(g,p))", computed on normal-behaviour datasets only, on points with normal status ID. — [Paper PDF Eq. 2](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content)
- Code: `accuracy_score(y_true=ground_truth, y_pred=predicted_anomalies)` (sklearn standard accuracy) on normal-status points. For a normal event with `ignore_normal_index=True` the ground truth is all False, so this reduces to TN/(TN+FP). Note: with `ignore_normal_index=False` (Farms B/C), ground truth is `~normal_index` but then filtered to `normal_index`, so it is also all-False. Equivalent. — [care_score.py](https://github.com/AEFDI/EnergyFaultDetector/blob/main/energy_fault_detector/evaluation/care_score.py)

**Reliability: criticality and event-level F-score (paper Algorithm 1)**
- Paper text: "Given the prediction timestamps t1,…,tN, the status information st_i ∈ {0,1} where 1 corresponds to a normal status and 0 to an abnormal status, and the prediction p_ti ∈ {0,1} where 1 represents a detected anomaly... crit ← [0,…,0]; for i: if st_i = 0 then [if p=1 crit[i]←crit[i−1]+1 else crit[i]←max{crit[i−1]−1,0}] else crit[i]←crit[i−1]". The algorithm's `if st_i = 0` contradicts the prose definition (1 = normal), so it is a typo. The code and FAQ increment on NORMAL-status points. — [Paper PDF Alg. 1](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content); [analysis.py](https://github.com/AEFDI/EnergyFaultDetector/blob/main/energy_fault_detector/utils/analysis.py)
- Code (`_compute_criticality_array`): `deltas = where(normal & anomaly, +1, where(normal & ~anomaly, -1, 0))`; `c = max(0, min(max_criticality, c + d))`, init 0, `max_criticality=1000` cap. Missing normal_idx values are treated as normal (True). With a MultiIndex, it is computed per group (asset). — [analysis.py `calculate_criticality`](https://github.com/AEFDI/EnergyFaultDetector/blob/main/energy_fault_detector/utils/analysis.py)
- Threshold: "the maximum criticality is compared to a threshold t_c, which we set to 72... in order to reach a criticality of 72, the algorithm must either detect at least 72 anomalies in a row, which equates to 12 h of consecutive anomalies... Setting the threshold at 72 was found to be the most appropriate for all 95 time series... For shorter events, a lower threshold is more appropriate." — [Paper PDF](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content)
- Paper wording: "If the threshold is exceeded ... detected anomaly event"; code uses `max_criticality >= criticality_threshold` (≥ 72). Default `criticality_threshold=72`. — [care_score.py](https://github.com/AEFDI/EnergyFaultDetector/blob/main/energy_fault_detector/evaluation/care_score.py); FAQ: "The default threshold ... is 72. You should of course tune this threshold for your dataset." — [FAQ](https://github.com/AEFDI/EnergyFaultDetector/blob/main/docs/care2compare_faq.rst)
- Code computes criticality only up to the event end: `calculate_criticality(anomalies=predicted_anomalies.loc[:event_end], normal_idx=normal_index.loc[:event_end])`. So the prediction-window padding BEFORE the event counts, and data after event_end is excluded. This applies to both normal and anomaly events. (The paper says "for the entire prediction time frame". This is a subtle deviation, and the code is the de-facto reference.) — [care_score.py](https://github.com/AEFDI/EnergyFaultDetector/blob/main/energy_fault_detector/evaluation/care_score.py)
- Event-level score: `fbeta_score(y_true=event_label=='anomaly', y_pred=anomaly_detected, beta=reliability_beta)` with default `reliability_beta=0.5`, computed once across all selected events (not averaged). — [care_score.py](https://github.com/AEFDI/EnergyFaultDetector/blob/main/energy_fault_detector/evaluation/care_score.py)
- Alternative event-detection mode exists: `anomaly_detection_method='fraction'` → detected if (tp+fp)/(tp+fp+fn+tn) ≥ `min_fraction_anomalous` (default 0.1). It is not the paper default. — [care_score.py](https://github.com/AEFDI/EnergyFaultDetector/blob/main/energy_fault_detector/evaluation/care_score.py)
- The code also records `first_time_detected` (first timestamp where criticality ≥ threshold) and `early_detection_time = event_end − first_time_detected` for anomaly events (informational, not part of CARE). — [care_score.py](https://github.com/AEFDI/EnergyFaultDetector/blob/main/energy_fault_detector/evaluation/care_score.py)

**Earliness: weighted score WS (paper Eq. 3)**
- "WS(p_a) = Σ_{i=1..M} w_ti·p_ti / Σ_{i=1..M} w_ti, where w_ti ∈ [0,1]"; timestamps are mapped to relative position [0,1] in the anomaly event; "In the first half of the event, all detected anomalies are assigned a weight of 1. In the second half of the event, the weights decrease linearly to 0". Computed only for anomaly events and only over the event window. — [Paper PDF Eq. 3, Fig. 1](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content)
- CODE DIFFERS: `ws_start_of_descend: Tuple[int,int] = (1, 4)` is the "Fraction ... where weights start to decay". Implementation: `scale=denominator(4)`, `L=len(event_prediction)*scale`, `cp=int(L*0.25)`, `x=np.linspace(0, scale, L)`, `weights[:cp]=scale`, `weights[cp:] = scale/(1-s) - x[cp:]/(1-s)` with s=0.25, then `weights = weights[::scale]/scale`; `WS = sum(pred*weights)/sum(weights)`. Net effect: weight 1 for the first 25% of the event, then linear decay to 0 at the end. To match the paper (decay from 50%), pass `ws_start_of_descend=(1, 2)`. The event window is `predicted_anomalies.loc[event_start:event_end]` (inclusive), and it is NOT filtered by status. — [care_score.py `_calculate_weighted_score`](https://github.com/AEFDI/EnergyFaultDetector/blob/main/energy_fault_detector/evaluation/care_score.py); arXiv v2 also states the first-half weighting — [arXiv v2](https://arxiv.org/html/2404.10320v2)

**Combination (paper Eqs. 4–5)**
- "WA := 1/Σω_i · (ω1·F̄β + ω2·W̄S + ω3·EFβ + ω4·Ācc), where we choose ω1 = ω2 = ω3 = 1 and ω4 = 2 in order to weight the normal datasets to the same degree as datasets containing an anomaly event, and β = 1/2." "CARE := 0, if no anomalies were detected; Acc̄, if Acc̄ < 0.5; WA, else." F̄β and W̄S are arithmetic means over anomaly datasets; Ācc is the mean over normal datasets. — [Paper PDF Eqs. 4–5](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content)
- Code `get_final_score`: requires ≥1 normal and ≥1 anomaly event (else ValueError). If `sum(anomaly_detected)==0` it returns 0 ("no anomalies detected" means no EVENT reached the criticality threshold, across all events including normal ones). If `avg_accuracy <= 0.5` it returns avg_accuracy (code uses ≤, paper uses <). Otherwise it returns `(2·acc + 1·WS + 1·F + 1·EF)/5`. Defaults: `coverage_w=1, accuracy_w=2, earliness_w=1, reliability_w=1`. — [care_score.py](https://github.com/AEFDI/EnergyFaultDetector/blob/main/energy_fault_detector/evaluation/care_score.py)
- Optional cost-weighted variant: F̄β^ω and W̄S^ω as importance-weighted means over anomaly datasets (paper Eqs. 6–7). It was not used in the benchmark. — [Paper PDF §3.3.5](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content)

**Trivial strategies**
- "the trivial strategies 'all anomaly' and 'all normal' both get the score 0 because they run into the special cases... The strategy 'random' gets the CARE score of 0.5 and sets the lower bound to beat... The isolation forest approach does not outperform that threshold". "Random" means each timestamp is independently anomaly with probability 0.5. — [Paper PDF §4.1, §4.3](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content)

### Inferences
- All-anomaly: Acc = 0, so CARE = Acc = 0. All-normal: no event is detected, so CARE = 0. Random: Acc ≈ 0.5 hits the Acc cap, so CARE ≈ 0.5. Under the code's `<=` rule, random returns ≈0.5 either way. In practice, any detector must keep mean normal-event accuracy > 0.5 and flag at least one event to score above trivial strategies. Accuracy carries 40% of the weight.
- Because the code's Coverage F-score uses the whole prediction series (padding before and after the event, with ground truth False there), false positives outside the event window lower Coverage precision. The F0.5 setting makes this penalty significant.
- Criticality is a bounded up/down counter, so 72 consecutive flags or a net surplus of 72 flags trigger an event detection. Intermittent flagging at ≤50% duty cycle never triggers it.
- For a faithful replication, use the package's `CAREScore` with defaults plus `ignore_normal_index=True` for Farm A. Report whether you used `ws_start_of_descend=(1,4)` (code default) or `(1,2)` (paper text).

### Gaps
- Numeric sub-scores of the paper's baselines are shown only in Figure 2 (bar chart). The text gives no numbers, so I could not extract them.
- The FAQ says the exact original paper code is not available, so it cannot be confirmed whether the paper's 0.66 used the 1/4 or 1/2 earliness descent point. — [FAQ "Is the exact original benchmark code available? Not exactly."](https://github.com/AEFDI/EnergyFaultDetector/blob/main/docs/care2compare_faq.rst)

## Q2. Which evaluation rows are used; status_type_id handling; Wind Farm A specifics

### Takeaway
Only `train_test == 'prediction'` rows are evaluated. "Normal" status = status_type_id ∈ {0, 2} in the paper's Table 2, but the reference loader uses `status_type_id == 0` only. For Wind Farm A, the status labels are ignored at prediction time (`ignore_normal_index=True`): every prediction timestamp is evaluated, and criticality moves at every step.

### Cited Findings
- Status table (paper Table 2): 0 "Normal operation without limitations" (normal: True); 1 "Derated power generation with a power restriction" (False); 2 "Asset is idling and waits to operate again" (True); 3 "Asset is in service mode/service team is at the site" (False); 4 "Asset is down due a fault or other reasons" (False); 5 "Other operational states for example system test, setup, ice build-up, or emergency power" (False). — [Paper PDF Table 2](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content)
- Farm A status derivation: "For each turbine fault, the preceding 14 days were marked with the status ID 4 (fault), and the 3 days after the fault timestamp were marked with the status ID 3 (service mode)." — [Paper PDF §3.1.3](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content)
- Reference loader: `normal_index = data['status_type_id'] == 0` (status 2 is NOT treated as normal). `x_test = dataset[dataset['train_test'] == 'prediction']`; `x_train = dataset[dataset['train_test'] == 'train']`. By default only the `avg` statistics are loaded. — [care2compare.py](https://github.com/AEFDI/EnergyFaultDetector/blob/main/energy_fault_detector/evaluation/care2compare.py)
- Notebook: "For WF A we cannot use the normal index to filter the events, as this would remove complete anomalous events (these are not based on actual SCADA Status codes)." `ignore_normal_idx = {'A': True, 'B': False, 'C': False}`. Train normal index is `status_type_id == 0`. — [CARE to Compare.ipynb](https://github.com/AEFDI/EnergyFaultDetector/blob/main/notebooks/CARE%20to%20Compare/CARE%20to%20Compare.ipynb)
- Guide: "For Wind Farm A, the status labels should mainly be used for training-data filtering. For prediction-time CARE evaluation, they should largely be ignored; pass `ignore_normal_index=True` to `evaluate_event` so that every timestamp is evaluated regardless of status_type_id." — [care2compare_guide.rst](https://github.com/AEFDI/EnergyFaultDetector/blob/main/docs/care2compare_guide.rst)
- FAQ: "Timestamps with abnormal status labels are excluded from pointwise evaluation... Note that we only apply this rule to wind farm B and C. For WF A, the status information can only be used for filtering training data and not for evaluation." Also: "For Wind Farm A the event labels were created based on available failure-log information." — [FAQ](https://github.com/AEFDI/EnergyFaultDetector/blob/main/docs/care2compare_faq.rst)
- Zenodo v6 note: for Farm A, status_type_id labels can be ignored when evaluating prediction windows with CARE, since they derive from the EDP failure logbook and are meant for training-data filtering. — [Zenodo 15846963](https://zenodo.org/records/15846963)
- `evaluate_event` options: `evaluate_until_event_end` (False default; True, 'normal_only', 'anomaly_only') caps data at event_end. The event_start and event_end come from `event_info.csv` (sep=';'), and the index must be timestamps (`index_column='time_stamp'`) to match. — [care_score.py](https://github.com/AEFDI/EnergyFaultDetector/blob/main/energy_fault_detector/evaluation/care_score.py); [guide](https://github.com/AEFDI/EnergyFaultDetector/blob/main/docs/care2compare_guide.rst)
- Dataset layout: 10-min resolution, 1 year training data plus 4–98 days of prediction data per dataset. "The prediction data are divided into an event time frame, with varying amounts of padding data before and after the event... to prevent guessing the event label." Farm A: 5 turbines, 22 datasets, 86 features, 54 sensors. As published in 2024: 11 anomaly / 11 normal. — [Paper PDF §3.1.2, Table 1](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content)
- Training requirement: "If at least 2/3 of the training data are normal behavior data, we define the sub-dataset to be sufficient", with ≥1 year of data. — [Paper PDF §3.1.1](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content)
- Timestamps are anonymized per file (shifted so each starts in 2022). Overlaps across event files are expected, and chronological order across files cannot be reconstructed. — [FAQ](https://github.com/AEFDI/EnergyFaultDetector/blob/main/docs/care2compare_faq.rst)

### Inferences
- Farm A implementation recipe: for each of 22 event IDs, load the `prediction` rows, produce a boolean anomaly series indexed by time_stamp, and call `evaluate_event(event_start, event_end, event_label, predicted_anomalies, normal_index, ignore_normal_index=True)`. Then call `get_final_score()` over Farm A event IDs.
- Ambiguity: the paper treats status 2 (idling) as normal, but the code uses only 0. For Farm A this does not matter at evaluation time (statuses are ignored), but it does affect training-data filtering. Since v5, Farm A has no status 5 (remapped to 0), so its statuses are effectively 0/3/4.

### Gaps
- I could not verify the exact v6 Farm A anomaly/normal split from the event_info file without downloading the 5.5 GB zip. v5 relabeled event 51 as an anomaly, and Zenodo now states 45 anomaly / 50 normal overall. A third-party repo reports Farm A as 12 anomaly / 10 normal, which is consistent if event 51 belongs to Farm A, but this is unverified (see Q3).

## Q3. Reported baseline scores and later papers reporting CARE scores

### Takeaway
The only official number is the overall CARE ≈ 0.66 for the per-turbine/per-event autoencoder NBM across all 95 datasets (random = 0.5, all-normal = 0, all-anomaly = 0, isolation forest < 0.5). The paper reports no per-farm CARE scores. I found no peer-reviewed 2024–2026 paper reporting an official-protocol CARE score on Farm A. One informal third-party repo reports Farm A CARE 0.608 (non-standard protocol).

### Cited Findings
- "With a score of 0.66, the AE approach represents a good anomaly detector"; results are over "all 95 sub-datasets" (Figures 2–3). AE: "high accuracy on normal data and a good performance on the event based F1/2-score, but it suffers a little bit from an overall low number of detected anomalies." — [Paper PDF §4.3](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content)
- Isolation forest baseline: sklearn `n_estimators=100`, `contamination=0.09`, PCA keeping 99% variance. Score is below 0.5. — [Paper PDF §4.1](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content)
- Farm A AE baseline: hidden layers 44, 25, 4, 25, 44; LR 0.0018; noise 0.06; batch 64; adaptive threshold (NN regressor of expected reconstruction error, 23 hidden units, γ = 0.344); anomaly if RE > ε + γ. Training uses 75% of normal data (25% validation), max 200 epochs, and early stopping with patience 3. Score = L2 norm of reconstruction error. Training data were additionally filtered with a wind-speed/power status. — [Paper PDF §4.2, Table 3](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content)
- Official config `windfarm_A.yaml`: clipping percentiles 0.001/0.999; column_selector `max_nan_frac_per_col: 0.05`; low_unique_value_filter (min 10 unique, max zero fraction 0.99); minmax scaler; AE layers [75, 44, 25], code_size 4, epochs 200, lr 0.0018241, noise 0.0600, MSE loss; anomaly_score `rmse`; threshold_selector `adaptive` (gamma 0.3441, nn_size 23, smoothing_parameter 6, fit_on_val true). — [windfarm_A.yaml](https://github.com/AEFDI/EnergyFaultDetector/tree/main/notebooks/CARE%20to%20Compare/c2c_configs)
- Notebook caveat: "The trained models may not reproduce the exact results reported in the paper due to random initialization... it is advisable to train each model 5–10 times and select the best-performing run." To reproduce the paper, an additional power-curve filter (cut-in/cut-out, P < 0.01) is needed, but only for wind farm C. The notebook prints per-farm A/B/C scores, but the committed version has no stored outputs. — [CARE to Compare.ipynb](https://github.com/AEFDI/EnergyFaultDetector/blob/main/notebooks/CARE%20to%20Compare/CARE%20to%20Compare.ipynb)
- FAQ: "In the dataset paper, individual autoencoder models per turbine were used." The notebook trains one model per event dataset, and it also shows a per-asset variant. — [FAQ](https://github.com/AEFDI/EnergyFaultDetector/blob/main/docs/care2compare_faq.rst)
- Third-party (informal, GitHub, not peer-reviewed): denoising AE with PCA, CARE Farm A 0.608 (Coverage 0.261, Accuracy 0.989, Reliability 0.714, Earliness 0.087; 4/12 faults detected, 0/10 false alarms); B 0.626; C 0.731. Isolation forest: A 0.518, B 0.611, C 0.733. A v2 rebuild gives Farm A 0.578. The repo uses its own CARE implementation, criticality threshold 36 (not 72), and thresholds tuned on the scored events. Not comparable. — [PeterImoniose/care-wind-turbine-predictive-maintenance](https://github.com/PeterImoniose/care-wind-turbine-predictive-maintenance)
- arXiv 2510.15010 (Nair et al., Oct 2025, "Hybrid Autoencoder-Based Framework for Early Fault Detection in Wind Turbines") uses the CARE dataset but reports AUC-ROC (A 0.912 / B 0.947 / C 0.963), F1, and so on. It reports no CARE score and uses its own 70/15/15 split. — [arXiv 2510.15010](https://arxiv.org/html/2510.15010v1)
- Fraunhofer's KonKIS 2024 talk slides restate the definitions (β = 0.5, criticality threshold 72, ω = 1,1,1,2) with no per-farm numbers. — [KonKIS24 slides](https://events.gwdg.de/event/615/contributions/2532/attachments/834/1567/Vortrag_KonKIS24_Care_to_Compare.pdf)
- Another informal student repo reports "86–91% accuracy" with KNN, which is not a CARE score. — [archiecrowley repo](https://github.com/archiecrowley/Wind-Turbine-Anomaly-Detection-Dissertation)

### Inferences
- Practical targets for Farm A: above 0.5 beats random, and about 0.6 is roughly what simple AE approaches reach. The official 0.66 is a pooled figure over 95 datasets and is not a Farm A number. Averaging per-farm scores is not the same as the pooled score.
- Typical AE failure mode on Farm A (from the third-party breakdown): very high Accuracy (~0.99) but low Coverage and Earliness. The detector is too conservative. Lowering γ or the criticality threshold trades accuracy for coverage.

### Gaps
- No per-farm official baseline numbers exist in the paper. Notebook outputs are not committed.
- My searches (web, arXiv) found no 2025–2026 peer-reviewed paper reporting official-protocol CARE scores. OUCI lists 2026 citing works (e.g., one in Electric Power Systems Research on ensemble fault diagnosis), but the page returned 403 and I could not check whether they report CARE scores. Google Scholar was not directly queryable. Absence of evidence ≠ evidence of absence.

## Q4. Official reference implementation (EnergyFaultDetector)

### Takeaway
`energy_fault_detector.evaluation.CAREScore` (per-event `evaluate_event`, then `get_final_score`) plus `Care2CompareDataset` loader. Defaults: β = 0.5/0.5, weights 1/2/1/1, criticality threshold 72, criticality method, earliness descent at 1/4. The criticality function is `energy_fault_detector.utils.analysis.calculate_criticality`. The default detector is an autoencoder with an RMSE anomaly score and either a quantile threshold (quickstart, 0.99) or an adaptive threshold (C2C configs).

### Cited Findings
- Constructor signature: `CAREScore(coverage_beta=0.5, reliability_beta=0.5, coverage_w=1., accuracy_w=2., earliness_w=1., reliability_w=1., criticality_threshold=72, min_fraction_anomalous=0.1, ws_start_of_descend=(1, 4), anomaly_detection_method='criticality')`. ### Inferences
- Minimal standalone re-implementation in Python, matching the code:
  1. Per event: `nidx = all True` (Farm A) or `status==0`.
  2. `gt = ~nidx`; for anomaly events, `gt[start:end] = True`.
  3. `F = fbeta(gt[nidx], pred[nidx], 0.5)` for anomaly events; `Acc = accuracy(gt[nidx], pred[nidx])` for normal events.
  4. `crit` = bounded counter over `pred[:end]` using `nidx[:end]`; `detected = crit.max() >= 72`.
  5. `WS` over `pred[start:end]` with the 1/4 (or 1/2) descent weights.
  6. Final score: `EF = fbeta(labels, detected, 0.5)`. If no event is detected, return 0. If mean Acc ≤ 0.5, return mean Acc. Otherwise return `(meanF + meanWS + EF + 2·meanAcc)/5`.

## Q5. Dataset v6 vs v5, known data issues, Farm A FAQ items

### Takeaway
v6 (Zenodo 15846963, 9 Jul 2025, 5.5 GB zip, CC BY-SA 4.0) is the latest version found. v5→v6 changes are metadata and unit fixes that are mostly Farm C, plus date fixes. Labels changed in v4→v5 (event 51 → anomaly; Farm A status 5 → 0; missing Farm A status 4 added). Min/Max/Std channels are often implausible, so prefer Avg. Farm A has wrapped pitch angles and inconsistent grid reactive power statistics.

### Cited Findings
- v6 metadata: published July 9, 2025; DOI 10.5281/zenodo.15846963; CARE_To_Compare.zip 5.5 GB, MD5 2547b58c21ac8c242d13232860cf500c; 95 datasets; "45 datasets contain a labeled anomaly ... 50 represent normal behavior" (the 2024 paper said 44/51). — [Zenodo 15846963](https://zenodo.org/records/15846963)
- v5→v6: Farm C sensor_40 and sensor_61 units changed from bar to hPa; event descriptions of events 34, 7, 19 changed to "high temperature in transformer cell"; dates corrected for events 44 and 47; event_info date format aligned with the dataset files; README typo fixed and README files re-added. — [Zenodo 15846963](https://zenodo.org/records/15846963)
- v4→v5: missing status_type_id 4 labels added for Farm A; event 51 relabeled as anomaly; Farm A status_type_id 5 changed to 0 ("came from a heuristic rather than ground truth"); `asset_id` column added to event_info. v3→v4: fixed duplicate timestamps from the leap-year anonymization shift. v2→v3: timestamp mismatches with event_info fixed. v1→v2: each sub-dataset starts in 2022. — [Zenodo 15846963](https://zenodo.org/records/15846963)
- Known issues (all farms): per-timestamp Min/Max/Std are often implausible, with four types: (1) Std higher than possible given Min/Max/Avg, (2) Min > Avg, (3) Max < Avg, (4) Min, Max, Std all zero. Avg values are generally plausible. Farm A: grid reactive power affected by issues 1 and 3; pitch angle shows angle-wrapping ambiguities (e.g., 0° vs 360°); other sensors have < 5% implausible Min/Max/Std. Farm B: use Avg only. Farm C: 17 sensors with 20–30% affected points, etc. — [Zenodo 15846963](https://zenodo.org/records/15846963)
- Paper data-quality notes: Farms B and C have 0 replacing missing values; status logging may be inconsistent; "status values for wind farm A were derived based on the EDP fault logbook... advisable to check the power and wind speed values in addition to the status values". Power and reactive power are scaled by rated power. — [Paper PDF §3.1.2, §3.1.4](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content)
- FAQ items relevant to Farm A: the event labels come from the failure log; status labels are for training filtering only; anomalous events can contain status 0 timestamps; the data is not preprocessed (needs NaN handling, angle transform, invalid filtering, scaling); Avg features are the safest; "Can benchmark scores vary when reproduced? Yes." — [FAQ](https://github.com/AEFDI/EnergyFaultDetector/blob/main/docs/care2compare_faq.rst)
- The paper's Data Availability statement points to the v4-era record 14006163. The concept DOI 10958774 and `records/14006163/latest` resolve to v6. — [Paper PDF](https://publica-rest.fraunhofer.de/server/api/core/bitstreams/6816cb77-9c66-424f-a41d-704432079311/content); [Zenodo latest](https://zenodo.org/records/14006163/latest)
